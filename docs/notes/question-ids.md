# Stable question ids and versions: maintainer notes

ADR 0003 section 3 (phase 1a-B). Migration `0008_questions.sql`, code in `src/lib/server/questions/`.

## How it works

- `questions.id` = the qkey (`src/lib/shared/qkey.ts`) of the question's **original** prompt. It never changes. So `review_items.qkey` and `attempts.qkey` written before this existed are already valid ids: nothing was rewritten.
- `question_versions` holds every wording. `questions.current_version_id` points at the live one (only an `approved` version can be current).
- **`question_versions.qkey` is an alias**: the qkey of THAT version's prompt. After an edit, the client still hashes the (new) prompt it shows, so the server maps any qkey to the canonical id (`resolveCanonicalId`) and `/api/attempts` stores the canonical id in `attempts.qkey`, `review_items.qkey` and the schedule. The client contract did not change.
- `createVersion` (no route yet): one `db.batch` that inserts version N+1 and moves the pointer. Refused when: stale (`expectedVersionId` is not current, or a concurrent edit took version N+1), retired, unknown, invalid, or the new wording hashes to ANOTHER question's id/alias (`qkey_collision`). It never touches `review_items` or `attempts`.
- `attempts.question_version_id`: filled by the server from the question's current version (or a client-sent id that belongs to the question). NULL for old rows and whenever the question is not registered.
- Pool rows: `questions.legacy_item_id` = `item_cache.id` (a join, `item_cache` is untouched). Registered by the backfill, and lazily by `/api/attempts` (`ensureQuestionForItem`) so new top-up rows need no step. An item_cache row identical to a curated question joins that question.
- Curated: `migrations/seeds/0008_questions_curated.sql` is GENERATED by `scripts/gen-question-seed.ts` from the Grade 6 registry (`reviewBanks.ts`); `questionSeed.test.ts` fails if it is stale. The code banks remain the fallback and are unchanged. Re-generate when a Grade 6 bank changes, then re-run the seed (it is idempotent, never overwrites an existing version, so an edit is never undone).

## Gotchas

1. **The review client still resolves from the code banks by `makeQkey(prompt)`.** Once a question is edited in D1 its new wording will not match the original id, so `/api/review/today` + the client would not find the text. Moving the source of truth to D1 must include resolving review candidates through `resolveQuestion`. Until then do NOT expose an edit route for questions that are in review.
2. A prompt change that happens in the code banks (not through `createVersion`) still orphans a schedule, exactly as before. The seed would register the reworded prompt as a NEW question. Edits belong in `createVersion`.
3. Duplicate (task, prompt) pairs inside a bank share one qkey, so they are one question (4 in `sinsbou`; the seed keeps the first). That is how review already treated them.
4. Curated seeding covers Grade 6 only (the registry). Grades 7-12 are not in review yet.
5. Label items with a React `Diagram` are seeded with `extra {"diagram":true}`; the component is not serialised, so D1 cannot render that item yet: the code bank stays the source for it.
6. `/api/attempts` is deploy-order safe: if 0008 is not applied, identity lookup throws, is caught, and the attempt is stored exactly as before.
7. The qkey-collision check and the version insert are separate statements (a tiny race). The UNIQUE (question_id, version_no) plus the conditional insert/update keep versions consistent; two simultaneous edits of DIFFERENT questions to the same new wording could still both pass the check. Fine for moderated edits; add a unique alias table if edits ever become high volume.

## Production runbook (owner; production migrations are applied with `wrangler d1 execute --remote --file`, never `migrations apply`)

Before anything: `git log` shows this branch merged. Run from the repo root. D1 is `preppals`, id `46f7b6a0-c555-4168-ae45-681dba2ceec2`.

0. Baseline (read only)
   ```
   npx wrangler d1 execute preppals --remote --command "SELECT (SELECT COUNT(*) FROM item_cache) AS pool, (SELECT COUNT(*) FROM review_items) AS reviews, (SELECT COUNT(*) FROM attempts WHERE qkey IS NOT NULL) AS qkey_attempts"
   grep -c "INSERT OR IGNORE INTO questions" migrations/seeds/0008_questions_curated.sql      # curated count, 1203 at the time of writing
   ```
1. Schema (additive; safe to run before the deploy: the old code ignores the new tables/column)
   ```
   npx wrangler d1 execute preppals --remote --file migrations/0008_questions.sql
   ```
   Check: `SELECT name FROM sqlite_master WHERE name IN ('questions','question_versions')` returns both; `SELECT COUNT(*) FROM pragma_table_info('attempts') WHERE name='question_version_id'` = 1.
2. Curated seed (one statement per line, 1.3 MB; if wrangler times out split it: `split -l 1200 migrations/seeds/0008_questions_curated.sql /tmp/seed-` and run each piece in order, the first piece has the two comment lines)
   ```
   npx wrangler d1 execute preppals --remote --file migrations/seeds/0008_questions_curated.sql
   ```
   Check: `SELECT source, COUNT(*) FROM questions GROUP BY source` shows curated = the grep count above; `SELECT COUNT(*) FROM questions WHERE current_version_id IS NULL` = 0; `SELECT COUNT(*) FROM question_versions` = `SELECT COUNT(*) FROM questions`.
3. Pool backfill. DRY RUN first (reads production with SELECT only, writes SQL files, changes nothing):
   ```
   node --import tsx scripts/backfill-question-ids.ts --source remote --out /tmp/question-ids
   ```
   It prints rows read, how many it would register and how many it skips (bad options JSON). Then apply:
   ```
   node --import tsx scripts/backfill-question-ids.ts --source remote --out /tmp/question-ids --apply --remote --confirm-prod=46f7b6a0-c555-4168-ae45-681dba2ceec2
   ```
   Check: `SELECT COUNT(*) FROM item_cache c LEFT JOIN questions q ON q.legacy_item_id = c.id WHERE q.id IS NULL` = the skipped count (normally 0), and the three orphan checks below. Re-running is harmless.
4. Orphan checks (every one must be 0)
   ```
   SELECT COUNT(*) FROM review_items r LEFT JOIN questions q ON q.id = r.qkey WHERE q.id IS NULL;
   SELECT COUNT(*) FROM attempts a LEFT JOIN questions q ON q.id = a.qkey WHERE a.qkey IS NOT NULL AND q.id IS NULL;
   ```
   A non-zero number is a curated-bank qkey that is not in the seed (a question whose wording changed since the learner answered it, or a non-Grade 6 bank). It is not a failure of the migration: those rows were already orphaned before; list them with the same query selecting `r.qkey, r.task`.
5. Deploy the code (it works with or without steps 1-3; steps 1-3 first means versions are recorded from the first answer).

Rollback: the code is safe to revert at any time (it only adds). To undo the data before anyone has edited a question: `DROP TABLE question_versions; DROP TABLE questions;` (the nullable `attempts.question_version_id` column and its index can stay, they are inert). After a real edit exists do not drop: the versions are the only copy of the edited wording.
